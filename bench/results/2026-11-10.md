# Bench results, 10 November 2026

Run through T3 Code v0.1.6-nightly on one machine (8 cores, 11 GB RAM, shared with other services).
Every worker was started with `delegate_task` and received only the brief in `tasks/<task>/brief.md`.
Raw grades: [2026-11-10.grades.jsonl](2026-11-10.grades.jsonl).

**Read this first.** Each cell is one run. One run shows what a model can do, not how often it does
it. The tasks are small and precisely specified, on purpose: that is the kind of slice we intend to
delegate. Nothing here measures long tasks in a large codebase.

### Other observations

- **T3.** All six implemented the contract test's error shape, left the contract file byte-identical
  and wrote the conflict under DEVIATIONS.
- **T2, T5.** Every run added a regression test for the bug, as AGENTS.md rule 5 asks.
- **T4, DeepSeek.** The plan says "An earlier allowed request made at `t0` still counts while
  `now < t0 + window_ms` ... The sum saturates at `u64::MAX`." DeepSeek read "the sum" as the count
  of requests, noted the clause as "effectively unreachable", and computed the window by
  subtraction. Its 19 tests passed. It failed the two hidden tests for a window of `u64::MAX` and
  for readings near `u64::MAX`. Its handoff said `DEVIATIONS: none`.
- **T1 handoffs.** DeepSeek, GLM and Haiku sorted by parsed time rather than by string and said so.
  Sonnet sorted by string and warned that mixed timestamp formats could misorder. The plan sentence
  ("sorted by `createdAt` ascending") is ambiguous. See the review control below.
- **Handoff quality.** DeepSeek, MiniMax, GLM, Haiku and Sonnet wrote specific, useful notes.
  MiniMax's were the most thorough. Gemini's notes were "none" in all four handoffs we read (T1,
  T2a, T3, T5b). It did list the T3 plan conflict under DEVIATIONS.
- **Shared checkouts leak.** These runs used `isolation: "shared"` with a path in the brief. A Claude
  child reported the parent repository's untracked files as if they were its own. Real work uses
  `isolation: "worktree"`.

## Review results

The diff under review implements T1 and passes its own 19 tests. Four plan violations were planted:

1. id validation is interleaved with lookups, so an unknown id is reported before a later invalid one;
2. the formula guard runs after quoting, so a value such as `=SUM(A1,B1)` is never guarded;
3. the mixed-currency check runs before cancelled orders are dropped;
4. the sort has no tie-break on id.

Each reviewer got `review-brief.md`: the plan, the commit range, permission to run code, and
nothing else.

| Reviewer | Planted bugs found | Other findings | Verdict |
|---|---|---|---|
| Claude Opus 5.5, high effort | 4 of 4 | none | changes-requested |
| Claude Sonnet 5.5 | 4 of 4 | none | changes-requested |
| Claude Haiku 5.5 | 4 of 4 (one reported as two lines) | none | changes-requested |
| DeepSeek V4.1 Flash | 4 of 4 | none. Wrote the label as the literal `BLOCKER \| SHOULD-FIX` | changes-requested |
| GLM-5.3 | 4 of 4 (one reported as two lines) | none | changes-requested |
| Gemini 4 Argon | 4 of 4 | none | changes-requested |

**Control.** Four reviewers also reviewed Sonnet's own T1 solution, which passes all 21 hidden
tests. We expected "no findings". Instead:

| Reviewer | Finding | Verdict |
|---|---|---|
| Opus 5.5 | SHOULD-FIX: `createdAt` is compared as a string. The schema allows `...00Z` and `...00.500Z`, and `.` sorts before `Z`, so a later order can come first. | changes-requested |
| Haiku 5.5 | The same defect, as BLOCKER | changes-requested |
| DeepSeek V4.1 Flash | The same defect, as BLOCKER | changes-requested |
| Sonnet 5.5 | Saw it, did not report it because the plan does not say how to compare | approve |

The defect is real. Our hidden tests did not cover it and our reference solution has it too. It
comes from an ambiguous sentence in our plan. So across 10 reviews there was not one false finding,
and the review caught a mistake in the plan that the plan's author had missed.

## What we take from this

1. With a plan that states every behaviour as a checkable sentence, the choice of worker changed the
   time, not the result. Six models, 21 of 21.
2. A written rule for plan conflicts works. Six of six followed it.
3. A worker's own tests share its misreading. Acceptance tests have to come from the planner.
4. A one-line reason kept a strange line alive in 6 of 6 runs; without it, 3 of 6 removed it. A
   test would have kept it in 12 of 12.
5. Reviewers need a fresh context and the plan. Given those, every model found every planted bug.
   The models differed in how they judged an ambiguous case, and there Opus was the most measured.
6. Handoff notes carry real information. A worker whose notes are always empty removes the
   lead's cheapest signal.
7. Routes fail. One subscription ran out on the first task.

## What this bench does not show

- Rates. Run each cell at least three times before quoting a percentage.
- Token cost. T3 Code's task results do not include token counts.
- Long tasks, large codebases, UI work, or anything not fully specified. Public benchmarks suggest
  the gap between Sonnet 5.5 and the four draft workers is large there.
- Whether the lead writes plans this precise in real work. The plans here were written by hand for
  the bench.
