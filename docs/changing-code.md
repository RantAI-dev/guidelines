# Changing code that already exists

Two jobs come up on every older project: bringing a repository up to these guidelines, and moving
code to another language. Both have the same shape. A script says what state things are in,
behaviour is pinned before anything moves, and the work goes in small slices that a cheap worker
can do and a script can check.

The step-by-step versions are skills an agent loads:
[adopt-guidelines](../template/.agents/skills/adopt-guidelines/SKILL.md) and
[port-code](../template/.agents/skills/port-code/SKILL.md). This page is the reasoning.

## Start either one

```bash
scripts/adopt.sh /path/to/repo
```

It prints the gaps, installs the template beside what is there without overwriting anything, and
tells you what to say to your agent next.

## Refactoring towards the guidelines

**1. A script audits; nobody reads the repository to find out.** `scripts/audit.sh` checks the
instruction files, the gate, tests, per-language counts and harness setup, and prints the gaps in
the order to close them. On one of our own services it listed 15 gaps in a few seconds.

**2. Get the gate green on the code as it is.** Configure the check; do not fix code yet. A gate
that starts red is ignored by everyone.

**3. Freeze, then pay down.** `scripts/ratchet.sh` records today's count of each violation, such
as a thousand `unwrap` calls. From then on a count may fall and may never rise. New code meets the rule
at once, and nobody has to fix a thousand lines before the first feature ships. When a count
reaches zero it becomes a lint rule. *Evidence:* judgement. This is how lint baselines and tools
like `betterer` work; we found no study of it with agents.

**4. Refactor only where work is coming.** An area gets refactored if a feature is planned there
or bugs keep coming from it. *Evidence:* measured, observational. Healthier code costs agents
fewer tokens and breaks less often under change, so the gain arrives where agents will work next.

**5. Pin behaviour before moving code.** Characterization tests record what the code does today,
including what looks wrong. They are written by the planner, committed and protected, and they are
the acceptance tests for every slice. *Evidence:* bench. A worker's own tests share its misreading.

**6. One kind of change per slice.** A move changes no logic. A boundary rule changes no
behaviour. A behaviour fix is its own pull request. A reviewer can check "nothing but renames";
nobody can check a move, a redesign and a fix mixed together.

## Moving code to another language

**The old code is the specification, and a script is the judge.** Three ports we looked at all
worked this way:

| Port | How "the same" was decided |
|---|---|
| Ladybird's JavaScript engine, C++ to Rust, about 25,000 lines in two weeks with coding agents (Feb 2026) | Byte-for-byte identical output from both pipelines across more than 65,000 tests, and a flag to run both in lockstep |
| Airbnb, 3,500 test files from one framework to another in six weeks (2025) | Each file went through fixed steps with a check after each, and was retried on failure. 97% finished automatically; people did the rest. |
| Our own `rantai-kb`, Bun to Rust (2026) | Reads moved first, then writes, then the old service was retired, with a rollback plan and 21 written "deliberate differences" |

What we take from them:

**1. Build the oracle before any port.** A command that runs the old implementation on a case and
prints the result. Case files are generated by it, never typed.

**2. Give the worker the oracle, not just the cases.** In our bench the brief said "ask the old
implementation about any case you invent". One worker generated 2,892 cases of its own before it
was done.

**3. Check with cases the worker has not seen.** Generate them with the oracle, aimed at where
languages differ. In the bench, a port that used Rust's ordinary rounding passed every visible
example and failed 24 of 367 hidden ones.

**4. Translate first, improve later.** Keep the structure and the names close to the old code so
the two can be compared. Ladybird's Rust deliberately still looks like C++. Idiomatic cleanup
comes after cutover, as a refactor with its own tests.

**5. Carry bugs over, and write differences down.** A bug in the old code is ported, listed and
fixed afterwards. Every intended difference is recorded with its reason. A difference that is not
on the list is a bug.

**6. Run both before switching, then delete the old one.** Shadow the new implementation on real
inputs, move reads, then writes, keep a rollback for an agreed time, and remove the old code in
the same week. Two live implementations drift.

**7. Most port bugs are in what the languages do differently, not in the logic.** Rounding of
ties, number width, remainder of negatives, text length, sort and map order, absent values, date
parsing, regular expressions. The skill has the full list; write cases for each line that applies.

## What the bench showed

One port task: a TypeScript pricing function to Rust, 12 visible cases, 367 hidden, an oracle the
worker may call. Details in [the results file](../bench/results/2026-11-10-port.md).

- The reference port matches 367 of 367. A naive port matches 343.
- MiniMax and DeepSeek both wrote ports that match 367 of 367, and both documented the rounding
  difference in the code. Neither run finished: the shared worker subscription hit its monthly
  limit before they committed, so these are not graded results. GLM-5.3 never started.

## Who does what

The same roles as any feature, and the same rule about the lead's budget: the lead writes the case
list and the ledger, scripts do the comparing, workers do the porting and the refactoring, and a
first-pass reviewer from the worker pool reads the diff.
